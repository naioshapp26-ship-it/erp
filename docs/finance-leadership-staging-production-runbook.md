# خطة Staging وProduction — القيادة المالية 360

**لا تنفيذ نشر دون موافقة صريحة.** هذا runbook فقط.

## 0) شروط ما قبل النشر (Go / No-Go)

| # | الشرط | الحالة عند الإغلاق |
|---|--------|-------------------|
| G1 | بوابة التحصيل 5a.3 مدمجة ومفعّلة في الكود (بدون علم) | جاهز في Draft |
| G2 | عزل اختبارات Finance عن public (دور + search_path) | جاهز محليًا |
| G3 | UNIQUE على JE ref + alloc | **ملف pending فقط** — يحتاج موافقة تطبيق |
| G4 | قرار ADVANCE معتمد ومنفّذ إن لزم | **بانتظار اعتماد** |
| G5 | أعلام `FINANCE_POST_*` | **false** حتى موافقة منفصلة |
| G6 | نسخة احتياطية DB قبل أي migration | إلزامي |
| G7 | عدم تأثر HR/Payroll/أرشيف في دخان Staging | يُنفَّذ بعد الموافقة |

## 1) ترتيب الدمج المقترح (بعد موافقتك على كل خطوة)

1. دمج سلسلة B1 حتى `b1d5a3-collection-gate` (أو squash closeout).
2. دمج عزل الاختبارات + ملفات UNIQUE pending + التقارير (هذا الفرع).
3. **موافقة منفصلة:** تطبيق UNIQUE على Staging فقط → دخان → ثم Production.
4. **موافقة منفصلة:** قرار ADVANCE (ب أو أ) ثم PR تنفيذ إن لزم.
5. **موافقة منفصلة:** تفعيل `FINANCE_POST_INVOICE_VIA_SERVICE` ثم `FINANCE_POST_PAYMENT_VIA_SERVICE` على Staging ساعة مراقبة.

## 2) Staging — خطوات التشغيل

1. Snapshot / backup قاعدة Staging.
2. نشر البناء المعتمد (بدون تفعيل أعلام).
3. دخان:
   - إنشاء فاتورة → قيد إصدار → تحصيل مخصص → تقارير.
   - محاولة تحصيل بلا قيد إصدار → 422.
   - مصروف + قيد يدوي + ميزان مراجعة/قائمة دخل.
   - HR أرشيف + payroll hub بدون انحدار.
4. (اختياري بعد موافقة) تطبيق UNIQUE CONCURRENTLY على Staging ومراقبة أخطاء 23505.
5. (اختياري بعد موافقة) تفعيل علم الفاتورة 24h ثم علم الدفعة 24h.

## 3) Production — خطوات التشغيل

1. نافذة صيانة قصيرة أو نشر متدرّج.
2. Backup كامل.
3. نشر الكود (أعلام false).
4. دخان محدود على كيان تجريبي.
5. تطبيق UNIQUE فقط بعد نجاح Staging + موافقة.
6. تفعيل الأعلام تدريجيًا بعد موافقة.

## 4) إيقاف التشغيل (Kill switch)

| إجراء | كيف |
|--------|-----|
| تعطيل مسار الخدمة | أزل/اترك `FINANCE_POST_*=false` وأعد تشغيل الخدمة |
| إيقاف تحصيل خاطئ | أعلام false تُبقي المسار القديم + بوابة 5a.3 ما زالت ترفض بلا قيد إصدار |
| سحب UNIQUE | `DROP INDEX CONCURRENTLY` بعد موافقة (نادرًا مطلوب) |

## 5) التراجع (Rollback)

1. رجوع إصدار التطبيق للبناء السابق.
2. لا تعكس قيودًا محاسبية تلقائيًا — أي عكس يدوي بموافقة مالية.
3. إن طُبّق UNIQUE ويسبب حظرًا مشروعًا: أبقِ الفهرس وراجع البيانات؛ لا تحذف الفهرس إلا بموافقة.

## 6) المراقبة

- معدلات 422 `INVOICE_ISSUE_JE_REQUIRED` و409 HUMAN_REVIEW.
- أخطاء `ALREADY_POSTED` / unique_violation بعد UNIQUE.
- زمن `POST /finance/payments` و`/invoices`.
- عدم ارتفاع أخطاء HR/Payroll.
- تنبيه إن تغيّر `journal_entry_id` لبذور `INV-FIN-*` دون تغيير معتمد.
