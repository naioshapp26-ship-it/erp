# القيادة المالية 360 — خطة تصميم P3
## دورة المبيعات والمحاسبة: عرض سعر → اعتماد → فاتورة → تحصيل → قيد محاسبي

**النوع:** تحليل وتصميم فقط — بلا كود / migrations / تعديل ترحيل في هذه الجولة.  
**الأساس التقني الحالي:** مخطط `finance_*` في `finance/database/init-finance-system.sql` + مسارات `finance/api/finance-routes.js`.  
**قيد حاسم:** لا دمج ولا نشر على Staging/Production دون موافقة صريحة.

## 0) خلاصة الوضع الحالي (نتائج الفحص)

| المرحلة | الواقع اليوم | الحكم |
|--------|-------------|--------|
| عرض سعر مبيعات | غير موجود. `finance_quick_offers` عروض ترويجية فقط | **Greenfield** (جدول/API جديد) |
| اعتماد | حقول متفرقة (`approval_state` للعروض الترويجية، mock في `rbac-system.js`) | **توحيد workflow** |
| فاتورة | `finance_invoices` + lines قوية؛ الإنشاء في `finance-routes` يرحّل قيدًا فورًا ويضبط الحالة `ISSUED` | **إعادة استخدام مع فصل الاعتماد عن الترحيل** |
| تحصيل | `finance_payments` + `finance_payment_allocations` + خطط أقساط؛ مسار مزدوج بدون تخصيص في `payments.js` | **توحيد على مسار التخصيص+القيد** |
| قيد محاسبي | `finance_journal_entries/lines` + ترحيل تلقائي عند إنشاء فاتورة/دفعة | **خدمة ترحيل موحّدة + عكس + منع التكرار** |
| ضريبة | `tax_settings` موجودة؛ حساب الفاتورة غالبًا 15% ثابت | **ربط فعلي** |
| عملات | لا عمود عملة/سعر صرف على فواتير `finance_*` | **إضافة اختيارية بمرحلة لاحقة أو P3.5** |
| عربون/خصومات متقدمة | واجهات localStorage فقط | **خارج نطاق P3 الأساسي** (دفعة اختيارية) |

**مبدأ إعادة الاستخدام:** بناء السلسلة على `finance_*` فقط. عدم خلط `tenant-migrations/002` أو `invoices_enhanced` أو bootstrap `ledger` في نفس الدورة.

## 1) ما يُعاد استخدامه مقابل ما يُنشأ

### إعادة استخدام (بدون جداول مكررة)
1. `finance_customers` — عملاء الذمم.
2. `finance_invoices` + `finance_invoice_lines` — مستند الفاتورة.
3. `finance_payments` + `finance_payment_allocations` — سند قبض + توزيع.
4. `finance_payment_plans` / `finance_plan_installments` — جدولة أقساط (اختياري ضمن التحصيل).
5. `finance_accounts` + `finance_journal_entries` + `finance_journal_lines` — دليل وقيود.
6. حسابات البذرة: `1130` ذمم، `1110/1120` نقد/بنك، `4100` إيراد، `2140` ضريبة.
7. `tax_settings` + `/api/tax-settings` — معدلات.
8. نطاق الكيان: `entity_type` / `entity_id` عبر `entity-context.js`.
9. واجهة تشغيلية مرجعية: `receivables-collections.html` (أغنى من master).
10. صلاحيات اسمية موجودة: `invoices.create|read|update|delete|approve` (تحتاج ربط خادمي حقيقي).

### Greenfield مطلوب
| عنصر | السبب |
|------|--------|
| `finance_sales_quotes` + `finance_sales_quote_lines` | لا يوجد مستند عرض سعر مبيعات |
| أعمدة/حالات اعتماد على الفاتورة قبل الترحيل | اليوم الإنشاء = ترحيل فوري |
| `POST …/cancel` و `POST …/reverse` للقيود | لا يوجد عكس محاسبي؛ الحذف الصلب مسموح |
| جدول/سجل `finance_posting_locks` أو قيد فريد `(reference_type, reference_id, posting_kind)` | منع الترحيل المكرر |
| إعدادات مستند فعلية (`finance_document_page_settings`) | إعدادات الصفحات الـ12 اليوم «قيد التطوير» |
| صلاحيات خادمية: `quotes.*`, `payments.approve`, `journals.post|reverse` | RBAC حاليًا mock جزئيًا |

### لا يُعاد استخدامه كعرض سعر
- `finance_quick_offers` يبقى تسويقًا ترويجيًا فقط (كما صحّح كتالوج P1).

## 2) نموذج المستندات وحالات الدورة

### 2.1 عرض السعر (جديد)
| الحالة | المعنى | انتقالات مسموحة |
|--------|--------|-----------------|
| `DRAFT` مسودة | قابل للتعديل الكامل | → `PENDING_APPROVAL`, `CANCELLED` |
| `PENDING_APPROVAL` بانتظار الاعتماد | قفل التعديل إلا لمن لديه صلاحية اعتماد | → `APPROVED`, `DRAFT` (رفض مع سبب), `CANCELLED` |
| `APPROVED` معتمد | جاهز للتحويل لفاتورة؛ صلاحية منتهية تمنع التحويل | → `CONVERTED`, `CANCELLED`, `EXPIRED` |
| `CONVERTED` محوّل | مرتبط بـ `invoice_id`؛ لا تعديل بنود | نهائي تشغيليًا |
| `EXPIRED` منتهي الصلاحية | تلقائي عند تجاوز `valid_until` | → `DRAFT` (إعادة إصدار بنسخة جديدة مفضّل) |
| `CANCELLED` ملغى | لا تحويل | نهائي |

**حقول أساسية مقترحة:** `quote_number`, `customer_id`, `quote_date`, `valid_until`, مبالغ (subtotal/tax/discount/total)، `currency_code` (افتراضي SAR)، `status`, `approved_by/at`, `converted_invoice_id`, `entity_*`, بنود مثل الفاتورة.

### 2.2 الفاتورة (موجودة — إعادة ضبط دلالات الحالات)
اليوم: الإنشاء يضبط `ISSUED` + قيد مرحّل.  
**المقترح التشغيلي:**

| الحالة | المعنى | الترحيل |
|--------|--------|---------|
| `DRAFT` | مسودة قابلة للتعديل | لا قيد |
| `PENDING_APPROVAL` | بانتظار اعتماد الإصدار | لا قيد |
| `APPROVED` | معتمدة جاهزة للترحيل | لا قيد بعد (أو ترحيل اختياري حسب إعداد الصفحة) |
| `ISSUED` / مرحّلة تشغيليًا | صادرة للعميل ومرحلّة محاسبيًا | **قيد واحد** مربوط بـ `journal_entry_id` |
| `PARTIAL` | محصّلة جزئيًا | مشتقة من التحصيل |
| `PAID` | مسددة بالكامل | مشتقة |
| `OVERDUE` | تجاوز الاستحقاق مع رصيد | مشتقة مجدولة |
| `CANCELLED` | ملغاة بعد الإصدار | عبر قيد عكسي؛ لا حذف |

`payment_status`: `UNPAID | PARTIAL | PAID` يبقى منفصلًا عن دورة الاعتماد.

**فصل مهم:** حالة المستند ≠ حالة القيد. القيد له دورة خاصة أدناه.

### 2.3 التحصيل / سند القبض
| الحالة | المعنى |
|--------|--------|
| `DRAFT` / `PENDING` | مسجّل بلا اعتماد/ترحيل |
| `APPROVED` | معتمد؛ الترحيل قد يكون تلقائيًا أو يدويًا حسب الإعداد |
| `POSTED` (إن أُضيف) أو الإبقاء على `APPROVED` + `journal_entry_id` | مرحّل محاسبيًا |
| `REJECTED` | مرفوض |
| `CANCELLED` | ملغى مع عكس إن كان مرحّلًا |

التخصيص عبر `finance_payment_allocations` إلزامي قبل الترحيل (مجموع التخصيص = مبلغ السند، أو فائض كرصيد عميل إن سُمح لاحقًا).

### 2.4 القيد المحاسبي
| الحالة | المعنى |
|--------|--------|
| `DRAFT` | قابل للتعديل؛ متوازن قبل الترحيل |
| `POSTED` | مرحّل؛ غير قابل للحذف/التعديل |
| `CANCELLED` | ملغى عبر قيد عكسي مرتبط (`reversal_of_entry_id`) وليس حذفًا |

يُقترح إضافة: `reversed_by_entry_id`, `reversal_of_entry_id`, و`UNIQUE(reference_type, reference_id, entry_type)` لمنع قيدَي INVOICE لنفس الفاتورة.

## 3) مخطط التحويلات (آلة الحالات)

```
[عرض سعر DRAFT]
    → submit → [PENDING_APPROVAL]
    → approve → [APPROVED]
    → convert → ينشئ [فاتورة DRAFT|PENDING_APPROVAL] + quote=CONVERTED

[فاتورة DRAFT]
    → submit → [PENDING_APPROVAL]
    → approve → [APPROVED]
    → post   → [ISSUED] + JE POSTED (Dr 1130 / Cr 4100 / Cr 2140)

[سند قبض PENDING]
    → allocate → invoices
    → approve(+post) → APPROVED + JE (Dr 1110|1120 / Cr 1130)
    → يحدّث paid/remaining → PARTIAL|PAID
```

## 4) مصفوفة الصلاحيات

| العملية | عرض سعر | فاتورة | سند قبض | قيد |
|---------|---------|--------|---------|-----|
| إنشاء | `quotes.create` | `invoices.create` | `payments.create` | `journals.create` (يدوي) |
| عرض | `quotes.read` | `invoices.read` | `payments.read` | `journals.read` |
| تعديل (مسودة فقط) | `quotes.update` | `invoices.update` | `payments.update` | `journals.update` إن DRAFT |
| اعتماد | `quotes.approve` | `invoices.approve` | `payments.approve` | اختياري `journals.approve` |
| ترحيل | — | `invoices.post` / `journals.post` | `payments.post` / ضمن الاعتماد | `journals.post` |
| إلغاء | `quotes.cancel` | `invoices.cancel` | `payments.cancel` | `journals.reverse` |

## 5) القيود المحاسبية المتوازنة ومنع الترحيل المكرر

### 5.1 قوالب القيود (SAR)
**إصدار فاتورة (ترحيل):**
- مدين `1130` ذمم = `total_amount`
- دائن `4100` إيراد = `subtotal - discount` (أو حسب بنود `revenue_account_id`)
- دائن `2140` ضريبة = `tax_amount`
- تحقق: Σ مدين = Σ دائن؛ وإلا رفض الترحيل.

**تحصيل:**
- مدين `1110` نقد أو `1120` بنك = `payment_amount`
- دائن `1130` = `payment_amount`
- بعد التخصيص: تحديث `paid_amount` / `remaining_amount` لكل فاتورة.

**عكس إلغاء فاتورة مرحّلة:**
- قيد جديد `entry_type=REVERSAL` يعكس أسطر الأصل؛ يربط `reversal_of_entry_id`.
- الفاتورة → `CANCELLED`؛ لا حذف أسطر تاريخية.

### 5.2 منع الترحيل المكرر
1. قيد فريد DB: `(reference_type, reference_id)` حيث `entry_type IN ('INVOICE','PAYMENT')` و`status='POSTED'`.
2. فحص تطبيقي داخل معاملة: `SELECT … FOR UPDATE` على المستند؛ إن وُجد `journal_entry_id` لترحيل من نفس النوع → رفض `409`.
3. اختياري: رأس `Idempotency-Key` على `POST …/post`.
4. إلغاء المسار المزدوج: إيقاف إنشاء قيد من مسارات لا تخصّص (`payments.js` بدون allocations) أو جعلها تفوّض لمسار `finance-routes` الموحّد.

### 5.3 قواعد الحذف/الإلغاء
| المستند | بعد الاعتماد/الترحيل |
|---------|---------------------|
| فاتورة | لا `DELETE`؛ فقط `cancel` + عكس قيد إن وُجد |
| قيد POSTED | لا حذف؛ فقط reverse |
| سند مرحّل | cancel + reverse + إعادة حساب أرصدة الفواتير |
| عرض سعر معتمد غير محوّل | cancel بدون قيد |
| عرض محوّل | لا إلغاء يعيد فتح الفاتورة؛ الإلغاء على الفاتورة منفصل |

## 6) عمليات الشاشات (CRUD وظيفي لكل صفحة)

### أ) صفحة عروض الأسعار (جديدة — تستبدل دلالة «عروض ترويجية» في مسار المبيعات)
- إضافة / عرض / تعديل مسودة / إرسال اعتماد / اعتماد-رفض / تحويل لفاتورة / إلغاء / بحث (عميل، رقم، حالة، تاريخ) / تصفية / طباعة PDF حسب قالب الإعدادات.
- لا حذف بعد `APPROVED`؛ نسخ جديد لإعادة الإصدار بعد الانتهاء.

### ب) صفحة الفواتير (تطوير `invoices-budgets-master` + مسار الإنشاء المفقود)
- إنشاء من صفر أو من عرض سعر.
- تعديل مسودة فقط.
- اعتماد → ترحيل (زر منفصل أو موحّد حسب إعداد الصفحة).
- عرض بنود + تخصيصات دفعات + رابط القيد.
- بحث/تصفية: عميل، حالة، استحقاق، كيان، رقم.
- طباعة فاتورة ضريبية وفق قالب.
- إلغاء مع سبب إلزامي.

### ج) التحصيل (`receivables-collections` كأساس)
- تسجيل سند + اختيار فواتير مفتوحة + مبالغ جزئية.
- منع تجاوز `remaining_amount` إلا بإعداد «سماح بالزيادة كرصيد».
- اعتماد/ترحيل، طباعة سند، إلغاء مع عكس.

### د) القيود (`journal`)
- عرض قيود AUTO من الدورة (للقراءة).
- إنشاء يدوي منفصل عن دورة المبيعات.
- ترحيل المسودات اليدوية؛ reverse للمرحّل.
- منع حذف المرحّل من الواجهة والـ API.

### هـ) العملاء / الضرائب
- العملاء كما هي (متطلب قبل العرض/الفاتورة).
- اختيار معدل من `tax_settings` عند البنود بدل ثابت 15%.

## 7) الدفعات الجزئية والمتبقي والضرائب والخصومات والعملات

| الموضوع | القاعدة المقترحة في P3 |
|---------|------------------------|
| دفعات جزئية | مسموحة إذا `allow_partial_payment=true`؛ كل تخصيص ≤ المتبقي؛ مجموع التخصيصات = مبلغ السند |
| المتبقي | `remaining = total - paid` يُحدَّث داخل نفس معاملة الترحيل |
| الضريبة | من `tax_settings` (افتراضي الكيان)؛ تُحسب على مستوى البند بعد الخصم؛ تُرحَّل إلى `2140` |
| خصم بند / خصم رأس | موجودان في المخطط؛ يُثبتان قبل الاعتماد؛ لا تعديل بعد الترحيل |
| خصومات ترويجية (`quick_offers`) | لا تُحوَّل تلقائيًا لعرض سعر؛ تطبيق يدوي اختياري لاحقًا |
| عملات | P3 الافتراضي: **SAR فقط**. إعداد `multi_currency_enabled` في إعدادات الصفحة؛ إن فُعّل لاحقًا: `currency_code` + `exchange_rate` + ترحيل بعملة الأساس |
| عربون | خارج P3 الأساسي؛ عند إضافته: التزام عميل ثم تخفيض ذمم عند الفوترة |

## 8) إعدادات الصفحات المؤثرة فعليًا على التشغيل

لكل من: عروض الأسعار، فواتير المبيعات، السندات، القيود — إعدادات تُخزَّن وتُقرأ عند الإنشاء/الطباعة/الترحيل:

| مفتاح إعداد | أثر تشغيلي |
|-------------|------------|
| `numbering_series` | سلسلة الترقيم (ربط بأنظمة الترقيم الحالية) |
| `default_tax_code` | معدل الضريبة الافتراضي |
| `require_approval_before_post` | فصل الاعتماد عن الترحيل |
| `auto_post_on_approve` | ترحيل تلقائي بعد الاعتماد |
| `print_template_id` | قالب الطباعة من `/settings/print-templates` |
| `default_payment_terms_days` | احتساب `due_date` |
| `allow_partial_payment` | وراثة على الفاتورة الجديدة |
| `default_revenue_account` / `default_ar_account` / `default_cash_account` | تجاوز حسابات البذرة |
| `approval_threshold_l1/l2` | عتبات الموافقين |
| `block_hard_delete_posted` | دائمًا true في الإنتاج |

هذا يحوّل بنود «إعدادات الصفحات» من coming_soon إلى تشغيل جزئي حقيقي على مستندات الدورة فقط (ليس كل الـ13 دفعة واحدة).

## 9) تغييرات قاعدة البيانات المتوقعة (للموافقة قبل التنفيذ)

> لا تُنفَّذ الآن — قائمة للمراجعة فقط.

1. **جداول جديدة:** `finance_sales_quotes`, `finance_sales_quote_lines`.
2. **أعمدة على `finance_invoices`:** `source_quote_id`, `approved_by/at`, ربما `posted_at/by` منفصلة، `currency_code` (افتراضي SAR).
3. **أعمدة على `finance_journal_entries`:** `reversal_of_entry_id`, `reversed_by_entry_id`.
4. **قيود فريدة:** منع ترحيل مكرر لنفس المرجع؛ منع تخصيص سالب/مفرط (triggers أو فحوص تطبيقية + CHECK).
5. **جدول إعدادات:** `finance_document_page_settings` (document_type, entity_id, settings JSONB).
6. **تشديد API:** إزالة/تعطيل `DELETE` للمرحّل؛ إضافة `cancel` / `post` / `reverse` / `convert`.
7. **توحيد المسارات:** مسار دفعات واحد يمر بالتخصيص قبل القيد.
8. **فهارس:** `(customer_id, status)`, `(source_quote_id)`, أرقام المستندات.

**مخاطر الترحيل الحالي:** فواتير موجودة أصلًا لها `journal_entry_id` بحالة `ISSUED` — خطة بيانات: اعتبارها «مرحّلة تاريخيًا» دون إعادة ترحيل؛ المسودات الجديدة فقط تتبع الآلة الجديدة.

## 10) التبعيات والمخاطر

| خطر | الأثر | تخفيف |
|-----|-------|--------|
| مسارات API مزدوجة للفواتير/المدفوعات | قيود مكررة أو سند بلا قيد | توحيد خدمة Posting قبل توسيع الواجهة |
| ترحيل فوري الحالي | يكسر دورة الاعتماد | feature flag: `defer_invoice_posting` |
| عملات غير مدعومة | تقارير مضللة | SAR فقط في P3 |
| RBAC mock | اعتماد شكلي | ربط خادمي + audit log |
| خلط `quick_offers` بعروض الأسعار | انحدار وظيفي | الإبقاء على فصل الكتالوج |
| عكس القيود يغيّر الأرصدة | تقارير الفترة | عكس بتاريخ يوم الإلغاء مع إشارة للفترة الأصلية |
| tenant schema الموازي | دفاتر مزدوجة | نطاق P3 = `finance_*` فقط |
| حذف صلب الحالي في journal API | فجوة رقابية | إيقاف الحذف للمرحّل أول دفعة ترحيل |

**تبعيات سابقة:** استقرار كتالوج P1 (تم)، عملاء صالحون، دليل حسابات بذرة، tax_settings للكيان.

**خارج النطاق الصريح لـ P3:** ZATCA/فاتورة إلكترونية حكومية، مخزون، مشتريات، عربون خادمي، خصومات localStorage→DB (دفعة لاحقة).

## 11) تقسيم التنفيذ إلى دفعات صغيرة

### الدفعة B0 — تجهيز وتصميم تقني معتمد
- اعتماد هذه الخطة + تجميد نطاق SAR + اختيار حسابات GL.
- **قبول:** وثيقة موافقة مكتوبة؛ قائمة migrations معتمدة دون تنفيذ.

### الدفعة B1 — توحيد خدمة الترحيل وحماية الدفاتر
- استخراج PostingService؛ منع حذف القيد المرحّل؛ reverse أساسي؛ idempotency على فاتورة/دفعة موجودة.
- **لا** تغيير UX كبير بعد.
- **قبول:**
  - محاولة ترحيل مكرر لنفس الفاتورة → 409.
  - حذف قيد POSTED → مرفوض.
  - reverse يوازن ويعكس الأثر على التقارير الأساسية.
- **اختبارات:** API integration على `:3010` مع مستأجر تجريبي؛ حالات إيجابية/سلبية موثّقة.

### الدفعة B2 — فصل إنشاء الفاتورة عن الترحيل + اعتماد
- حالات DRAFT → PENDING_APPROVAL → APPROVED → post→ISSUED.
- واجهة إنشاء فاتورة (المسار الناقص اليوم).
- **قبول:** فاتورة جديدة لا تُنشئ قيدًا قبل post؛ بعد post يظهر `journal_entry_id`؛ تعديل المرحّل مرفوض.
- **اختبارات:** Puppeteer إنشاء/اعتماد/ترحيل؛ تحقق صفوف JE متوازنة في DB.

### الدفعة B3 — عروض الأسعار + التحويل لفاتورة
- جداول quotes؛ شاشة كاملة؛ convert ينسخ البنود والضريبة.
- **قبول:** تحويل عرض معتمد ينشئ فاتورة مسودة مرتبطة؛ عرض محوّل غير قابل لإعادة التحويل؛ منتهي الصلاحية يُرفض.
- **اختبارات:** دورة E2E Quote→Invoice؛ صلاحيات approve.

### الدفعة B4 — التحصيل الجزئي والتخصيص الموحّد
- تعطيل مسار الدفع بلا تخصيص؛ UI تخصيص إلزامي؛ تحديث PARTIAL/PAID.
- **قبول:** دفعتان جزئيتان تغطيان الفاتورة؛ المتبقي صفر؛ قيدان تحصيل منفصلان؛ منع تجاوز المتبقي.
- **اختبارات:** سيناريوهات partial/overpay/cancel-with-reverse.

### الدفعة B5 — إعدادات الصفحات التشغيلية للمستندات الأربعة
- تخزين إعدادات + أثر على الترقيم/الضريبة/الاعتماد/القالب.
- **قبول:** تغيير `default_tax_code` يظهر في فاتورة جديدة؛ قالب الطباعة يُحمَّل؛ البنود غير المرتبطة بالدورة تبقى coming_soon.
- **اختبارات:** قراءة إعدادات عبر API؛ لقطة طباعة.

### الدفعة B6 — صقل الكتالوج والتقرير النهائي
- تحديث شارات القيادة المالية للصفحات التي أصبحت تشغيلية جزئيًا/كاملًا.
- تقرير PASS/FAIL + عدم كسر HR/أرشيف.
- **قبول:** مطابقة الكتالوج للواقع؛ لا نشر دون موافقة.

## 12) معايير قبول أفقية لكل دفعة
1. لا migrations على Staging/Production دون موافقة.
2. Draft PR فقط لكل دفعة.
3. اختبارات حقيقية (API + UI) وليس فتح الرابط فقط.
4. قيود متوازنة 100% في العينات المختبرة.
5. Audit: من أنشأ/اعتمد/رحّل/ألغى مع طابع زمني.
6. عدم حذف بيانات تاريخية مرحّلة.
7. عدم كسر روابط كتالوج P1 القائمة.

## 13) قرارات تحتاج موافقة صريحة قبل البرمجة
1. هل الترحيل يتم تلقائيًا عند الاعتماد أم بزر منفصل؟ (الخطة تدعم الإعداد؛ الافتراض المقترح: **زر منفصل** للرقابة).
2. هل التحويل من عرض سعر ينشئ فاتورة `DRAFT` أم `PENDING_APPROVAL` مباشرة؟
3. هل نبدأ B1 (حماية الدفاتر) قبل أي UI لعروض الأسعار؟ (**موصى به**).
4. نطاق العملات: تأكيد **SAR فقط** في P3.
5. هل تُدرج صلاحيات العتبات 10k/50k في B2 أم تُؤجَّل؟
